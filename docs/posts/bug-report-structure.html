Bug Bounty보고서재현
블로그 구성을 위한 예시 노트이다. 실제 문제 풀이, 취약점 제보, 수상 또는 자격 취득 실적을 의미하지 않는다.

읽는 사람이 재현할 수 있어야 한다

취약점 보고서는 문제를 처음 보는 사람이 내용을 이해하고 확인할 수 있도록 작성한다. HackerOne의 보고서 품질 안내는 명확한 제목, 재현 단계, 영향 설명, 보조 자료를 주요 요소로 제시한다. 제보 전에는 발견한 문제가 프로그램 범위에 포함되는지도 확인한다.

제목에는 대상 기능과 문제가 되는 동작을 구체적으로 적는다. 본문 첫 문단에는 필요한 조건과 관찰한 결과를 짧게 요약한다.

재현 조건과 순서를 분리한다

계정 역할, 제품 버전, 기능 설정처럼 먼저 갖추어야 하는 조건을 적고, 그다음 실행 순서를 번호로 작성한다. 화면을 클릭한 순서만 나열하기보다, 각 단계에서 무엇을 입력하고 어떤 결과를 확인했는지 연결한다.

구역 답해야 할 질문
요약 어떤 기능에서 어떤 동작을 관찰했는가?
전제 조건 어떤 권한과 환경이 필요한가?
재현 단계 같은 결과를 확인하려면 무엇을 해야 하는가?
결과 정상적으로 기대한 동작과 실제 동작은 무엇인가?
영향 검증한 범위에서 어떤 문제가 발생하는가?

검증한 영향만 설명한다

관찰한 결과와 추가 검증이 필요한 가능성을 구분한다. 한 가지 상황에서 확인한 결과를 제품 전체의 영향으로 확장해서 쓰지 않는다. 영향이 특정 권한이나 설정에 의존한다면 그 조건도 함께 남긴다.

증거 자료는 해당 설명을 뒷받침하는 부분을 고른다. 로그의 어느 줄이 어떤 단계와 연결되는지 표시하면 보고서를 다시 읽을 때 맥락을 찾기 쉽다.

공개 보고서로 작성 연습하기

처음에는 공개된 보고서 한 편을 골라 요약, 조건, 재현, 영향으로 다시 나누어 읽어 본다. 비어 있는 정보를 추측으로 채우지 않고 질문으로 남긴다. 예를 들어 “이 결과에 관리자 권한이 필요한가?”처럼 적는 방식이다.

이 카테고리에서는 앞으로 공개 자료에 대한 학습 노트와 직접 수행한 활동을 제목과 본문에서 분명히 구분할 수 있다. 실제 제보 내용을 글로 옮길 때는 해당 프로그램의 공개 조건을 확인한다.
