### 논문 정보

- **제목:** HouseFuzz: Service-Aware Grey-Box Fuzzing for Vulnerability Detection in Linux-Based Firmware
- **저자:** Haoyu Xiao, Ziqi Wei, Jiarun Dai, Bowen Li, Yuan Zhang, Min Yang
- **학회:** 46th IEEE Symposium on Security and Privacy (S&P)
- **연도:** 2025

### 이 논문을 고른 이유

현재 IP 카메라 취약점 분석 프로젝트를 진행하면서, 네트워크 요청을 받는 하나의 바이너리만 분석해서는 IPC로 연결된 내부 데몬과 커스텀 프로토콜의 공격 표면을 충분히 확인하기 어렵다고 느꼈다. HouseFuzz는 펌웨어 서비스를 여러 프로세스가 협력하는 하나의 서비스 단위로 분석하고, 커스텀 프로토콜의 의미적 제약까지 퍼징에 반영한다. 이러한 접근 방식을 현재 프로젝트에 활용할 수 있을 것으로 생각하여 이 논문을 선택했다.

### Linux 기반 펌웨어 프로세스

HouseFuzz는 분석 편의를 위해 펌웨어 서비스의 프로세스를 다음 세 유형으로 분류한다.

![펌웨어 서비스의 프로세스 분류](../assets/posts/housefuzz-review/firmware-service-processes.png)

```txt
펌웨어 서비스의 프로세스
├── 장기 실행 프로세스
│   ├── Network-facing process
│   │   └── 원격에서 접근 가능한 지속적 채널 제공
│   └── Daemon process
│       └── 로컬에서만 접근 가능한 지속적 채널 제공
└── 유틸리티 프로세스
    └── 장기 실행 프로세스가 단기 작업 처리를 위해 호출
```

### IPC(Inter-Process Communication)

IPC는 서로 독립된 프로세스가 데이터를 주고받는 방법이다. 각 프로세스는 별도의 메모리 공간을 가지므로, 다른 프로세스의 함수를 일반 함수처럼 직접 호출하거나 메모리를 직접 읽을 수 없다. 따라서 소켓, 파이프, 공유 메모리, 메시지 큐와 같이 운영체제가 제공하는 통신 수단을 사용해야 한다.

HouseFuzz의 ***3.1절 Motivating Example***에서 `mini_httpd`와 `ncc`는 **loopback TCP/IP 소켓**을 이용해 통신한다.

| 프로세스 | 역할 | 대기 주소 | 접근 범위 |
| --- | --- | --- | --- |
| `mini_httpd` | 외부 HTTP 요청을 직접 받는 network-facing process | `0.0.0.0:80` | 외부 네트워크에서 접근 가능 |
| `ncc` | 내부 요청을 실제로 처리하는 daemon process | `127.0.0.1:0xFF80` | 같은 장치 내부에서만 접근 가능 |

`0.0.0.0:80`은 장치의 모든 네트워크 인터페이스에서 들어오는 HTTP 요청을 받기 위한 외부 채널이다. 반면 `127.0.0.1`은 장치 자신을 가리키는 loopback 주소이므로, `ncc`의 소켓은 외부에서 직접 접근할 수 없는 내부 IPC 채널이다. 소켓을 사용하더라도 동일한 장치의 두 프로세스가 통신하는 것이므로 IPC에 해당한다.

#### `mini_httpd`에서 `ncc`로 요청이 전달되는 과정

1. 시스템 부팅 과정에서 `ncc`가 실행되고, `127.0.0.1:0xFF80`에서 내부 요청을 기다린다.
2. `ncc`가 `system("mini_httpd ...")`를 호출하여 `mini_httpd`를 실행한다.
3. 공격자가 `mini_httpd`의 80번 포트로 HTTP 요청을 전송한다.
4. `mini_httpd`가 HTTP 요청을 파싱하고 요청 경로가 `.ccp`로 끝나는지 검사한다.
5. `.ccp` 요청이면 `build_ipc_data()`를 통해 내부 전달용 데이터를 생성한다.
6. `ncc_socket_send()`가 생성된 데이터를 `ncc`의 loopback TCP/IP 소켓으로 전송한다.
7. `ncc`의 `select`가 데이터 도착을 감지하고 `ipc_handler()`를 실행한다.
8. `ncc`가 `ccp_act`, `nextPage`, `pc_ip` 등의 커스텀 파라미터를 검사한 뒤 취약한 코드에 도달한다.

```txt
외부 공격자
    │
    │ HTTP 요청: POST /get_set.ccp
    ▼
mini_httpd
(network-facing process, 0.0.0.0:80)
    │
    │ build_ipc_data()
    │ ncc_socket_send()
    ▼
loopback 소켓 IPC
(127.0.0.1:0xFF80)
    │
    ▼
ncc
(daemon process)
    │
    │ ipc_handler() → get_set_callback()
    ▼
커스텀 파라미터 검사 → 취약한 sprintf() → 버퍼 오버플로
```

#### 퍼징 관점에서 IPC가 중요한 이유

`mini_httpd`는 외부 요청을 수신하고 이를 내부 요청으로 변환하여 전달할 뿐이며, 실제 취약한 코드는 `ncc`에서 실행된다. 따라서 `mini_httpd`만 퍼징하고 코드 커버리지를 수집하면 `ncc`에서 새 코드가 실행됐는지 또는 충돌이 발생했는지 관찰할 수 없다. HouseFuzz가 두 프로세스를 하나의 서비스로 취급하고, 모든 관련 프로세스의 코드 커버리지와 취약점 발생 여부를 함께 관찰하는 이유가 여기에 있다.

## 이 논문이 등장한 배경과 문제의식

---

Linux 기반 펌웨어의 네트워크 서비스는 주요 공격 표면이며, 그레이박스 퍼징은 이러한 서비스의 취약점을 탐지하는 핵심 기법으로 사용되어 왔다. 그러나 기존 방식은 펌웨어 서비스의 **다중 프로세스 구조**와 **프로토콜 커스터마이징**을 충분히 고려하지 못한다.

Linux 기반 펌웨어의 서비스는 하나의 프로세스가 아니라, 네트워크 요청을 직접 받는 프로세스와 여러 데몬 프로세스의 협력으로 동작한다. 기존 방식은 서비스에 필요한 프로세스를 포괄적으로 식별하지 못하기 때문에, 일부 데몬 프로세스를 제외한 채 서비스를 불완전하게 에뮬레이션할 수 있다. 이 경우 퍼징 가능한 서비스의 수와 코드 탐색 범위가 제한된다.

또한 기존 그레이박스 퍼징은 다중 프로세스 서비스를 단일 프로세스로 단순화하고, 네트워크 요청을 직접 받는 프로세스의 실행 피드백만을 수집하는 경우가 많다. 따라서 다른 프로세스에서 실행되는 코드와 프로세스 간 상호작용을 관찰하지 못하며, 여러 프로세스의 협력이 필요한 취약점을 탐지하기 어렵다.

펌웨어 서비스에는 표준 프로토콜뿐 아니라 제조사가 추가한 커스텀 서비스 프로토콜도 사용된다. 기존 protocol/grammar-aware fuzzing은 주로 표준 프로토콜의 구문과 일반적인 의미 규칙을 모델링하므로, 펌웨어별 토큰 간 의존관계와 같은 애플리케이션 고유의 의미적 제약을 충분히 반영하지 못한다. 그 결과 생성된 입력이 서비스의 초기 검증 단계에서 거부되어 깊은 실행 경로에 도달하기 어렵다.

따라서 효과적인 취약점 탐지를 위해서는 다음 조건이 필요하다.

1. 서비스와 관련된 네트워크 프로세스와 데몬 프로세스를 모두 식별하고 에뮬레이션해야 한다.
2. 여러 프로세스에서 발생하는 실행 피드백을 통합하여 퍼징을 안내해야 한다.
3. 표준 프로토콜 문법뿐 아니라 펌웨어별 커스텀 의미 제약을 만족하는 입력을 생성해야 한다.

## 저자들이 제안한 핵심 접근 방식

---

HouseFuzz는 펌웨어 이미지와 표준 서비스 프로토콜을 입력으로 받아 다음 세 가지 기법을 결합한다.

> **논문 위치:** 1절 Contributions, 4절 Overview of HouseFuzz, 그림 2

### 1. 포괄적 서비스 식별 및 에뮬레이션

기존 프로세스 에뮬레이션 방식은 프로세스 이름 화이트리스트에 의존하기 때문에 목록에 없는 network-facing process와 데몬 프로세스를 놓칠 수 있다. 반면 시스템 에뮬레이션 방식은 전체 시스템을 실행하지만, 초기화 과정에서 발생하는 예외로 인해 네트워크·IPC 채널이 생성되기 전에 중단될 수 있다.

> **논문 위치:** 1절의 ❶ Limitations in Service Emulation, 3.2절 Challenges

HouseFuzz는 초기화 절차에서 생성되는 네트워크·IPC 채널을 추적하여 서비스 관련 프로세스를 식별하고, 이를 하나의 서비스 단위로 구성한다. 구체적인 구현 도구와 예외 코드 패치 과정은 뒤의 「시스템 구성」에서 설명한다.

> **논문 위치:** 2.1절의 service 정의, 3.2절 Key Insights, 5.1절 Holistic Service Identification

### 2. 다중 프로세스 그레이박스 퍼징

HouseFuzz는 서비스에 참여하는 모든 프로세스의 실행 피드백을 수집하는 사용자 공간 다중 프로세스 퍼징 프레임워크를 제안한다.

> **논문 위치:** 3.3절 Key Insights, 4절 Overview, 6절 Multi-Process Fuzzing Framework

프레임워크는 다음 두 기능으로 구성된다.

- **다중 프로세스 커버리지 기반 안내:** 관련 프로세스에서 수집한 코드 커버리지를 병합하여 퍼징을 안내한다.
- **다중 프로세스 취약점 탐지:** 여러 프로세스에서 발생하는 취약점을 다중 프로세스 취약점 오라클로 탐지한다.

> **논문 위치:** 4절 Overview, 6.1절 Multi-Process Coverage Guidance, 6.2절 Multi-Process Vulnerability Detection

HouseFuzz는 TCE(Test Completion Event) 탐지를 이용해 테스트 케이스 실행이 끝나는 시점을 판단하고, 적절한 시점에 다중 프로세스 코드 커버리지를 수집한다.

> **논문 위치:** 6.1절, 8.4.3절 Experiment on TCE Detection Stability

예를 들어 `mini_httpd`가 외부 HTTP 요청을 받아 IPC를 통해 `ncc`로 전달하면, HouseFuzz는 `mini_httpd`뿐만 아니라 `ncc`의 코드 커버리지와 취약점 발생 여부도 관찰한다.

> **논문 위치:** 3.1절 Motivating Example, 그림 1, 3.3절

### 3. 서비스 프로토콜 기반 퍼징

HouseFuzz는 서비스 프로토콜을 다음 두 부분으로 구분한다.

- **표준 서비스 프로토콜:** HTTP와 같은 프로토콜의 구문 구조
- **커스텀 서비스 프로토콜:** 펌웨어 제조사가 추가한 토큰과 의미적 제약

> **논문 위치:** 2.2절 Service Protocols of Linux-Based Firmware, 7.1절 Formalization of Service Protocol

커스텀 서비스 프로토콜의 의미적 제약은 **TDG(Token Dependency Graph)로** 표현한다.

- TDG의 노드는 프로토콜 입력에 사용되는 토큰을 나타낸다.
- TDG의 간선은 토큰 사이의 의존관계를 나타낸다.
- 오프라인 제어·데이터 흐름 분석으로 초기 TDG를 생성한다.
- 온라인 계측 분석으로 실행 중 발견되는 토큰과 의존관계를 추가한다.

> **논문 위치:** 1절 Introduction, 7.1절 Service Protocol, 7.2절 Service Protocol Inference

HouseFuzz는 표준 프로토콜 문법으로 구문적 유효성을 확보하고, TDG를 통해 커스텀 의미 제약을 만족할 가능성을 높인다. 이를 통해 초기 입력 검증을 통과하고 더 깊은 코드 경로에 도달하도록 입력 생성을 안내한다.

> **논문 위치:** 3.4절 Key Insights, 7.3절 Service-Protocol-Guided Test Case Generation

## 시스템 구성

---

앞 절에서 설명한 세 가지 핵심 접근 방식은 각각 독립적으로 동작하는 것이 아니라, 하나의 분석·퍼징 파이프라인으로 구현된다. HouseFuzz는 기존 도구를 조합하고 확장하여 **펌웨어 추출 → 서비스 식별 → 프로세스 에뮬레이션 → 프로토콜 추론 → 다중 프로세스 퍼징 → 취약점 분석**을 수행한다.

> **논문 위치:** 4절 Overview of HouseFuzz, 그림 2, 8.1절 Prototype

### 전체 처리 과정

```txt
펌웨어 이미지 + 표준 서비스 프로토콜
                │
                ▼
Binwalk
펌웨어 파일시스템 추출
                │
                ▼
QEMU User Mode
시스템 초기화 절차 실행
시스템 호출·기본 블록 실행 추적
                │
                ▼
Radare2
실행 추적 분석
에뮬레이션 예외 코드 탐지·패치
                │
                ▼
네트워크 서비스와 관련 프로세스 식별
                │
        ┌───────┴──────────────────┐
        ▼                          ▼
IDA Pro 기반 정적 분석         Greenhouse 기반
오프라인 TDG 생성              프로세스 에뮬레이션
        │                          │
        └───────────┬──────────────┘
                    ▼
수정된 AFL++ QEMU Mode
├── 다중 프로세스 코드 커버리지 수집
├── 다중 프로세스 취약점 오라클
└── 온라인 TDG 추론
                    │
                    ▼
표준 프로토콜 문법 + TDG 기반
테스트 케이스 생성
                    │
                    ▼
다중 프로세스 그레이박스 퍼징
                    │
                    ▼
코드 커버리지 및 취약점 분석
```

### 구현 규모

HouseFuzz 프로토타입은 약 7,000줄의 C 코드와 5,000줄의 Python 코드로 구현되었다.

> **논문 위치:** 8.1절 Prototype

### 구성요소별 역할

| 구성요소 | 역할 |
| --- | --- |
| Binwalk | 펌웨어 이미지에서 파일시스템 추출 |
| QEMU User Mode | 시스템 초기화 절차와 서비스 프로세스 실행 |
| QEMU 실행 추적 | 시스템 호출과 기본 블록 실행 기록 |
| Radare2 | 실행 추적을 분석하여 에뮬레이션 예외 코드를 찾고 패치 |
| IDA Pro 기반 분석 엔진 | 서비스 바이너리를 정적으로 분석하여 오프라인 TDG 생성 |
| Greenhouse | 식별된 서비스 프로세스의 프로세스 에뮬레이션 |
| 수정된 AFL++ QEMU Mode | 커버리지 기반 테스트 케이스 변형 및 실행 |
| 다중 프로세스 피드백 모듈 | 관련 프로세스의 코드 커버리지를 수집하고 병합 |
| 다중 프로세스 취약점 오라클 | network-facing process 외의 프로세스에서 발생한 취약점 탐지 |
| 온라인 TDG 추론 모듈 | 실행 중 관찰된 토큰과 의존관계를 TDG에 반영 |

> **논문 위치:** 8.1절 Prototype
>
> **세부 설계:** 5절 Service Emulation, 6절 Multi-Process Fuzzing Framework, 7절 Service-Protocol-Guided Fuzzing

### 시스템 초기화와 서비스 식별

HouseFuzz는 QEMU User Mode에서 펌웨어의 시스템 초기화 절차를 실행한다. 실행 과정에서 시스템 호출과 기본 블록을 추적하여 프로세스 생성, 네트워크 채널, IPC 채널을 관찰한다.

초기화 과정에서 프로세스 충돌과 같은 예외가 발생하면 Radare2로 실행 추적을 분석하여 예외 코드를 찾아 패치한다. 이를 통해 초기화가 중간에 중단되는 것을 완화하고, 기존 방식이 놓쳤던 네트워크 서비스와 관련 데몬 프로세스를 추가로 식별한다.

> **논문 위치:** 5.1절 Holistic Service Identification, 8.1절 Prototype

### 프로토콜 분석

서비스 바이너리는 IDA Pro 기반 엔진이 제어·데이터 흐름을 정적으로 분석하여 오프라인 TDG를 생성한다. 퍼징 중에는 수정된 AFL++ QEMU Mode가 문자열 비교 연산과 실행 정보를 계측하여 온라인 TDG를 갱신하며, 두 분석 결과는 테스트 케이스 생성 모듈로 전달된다.

> **논문 위치:** 7.2절 Service Protocol Inference, 8.1절 Prototype

### 다중 프로세스 퍼징

식별된 서비스는 Greenhouse 기반 프로세스 에뮬레이션으로 실행된다. 수정된 AFL++ QEMU Mode가 프로세스별 coverage bitmap과 취약점 oracle을 관리하며, `execve()` 계측으로 새로 생성된 utility process까지 추적한다. 이를 통해 서비스에 참여하는 프로세스별 실행 피드백을 하나의 퍼징 피드백으로 통합한다.

> **논문 위치:** 6절 Multi-Process Fuzzing Framework, 8.1절 Prototype

## 실험 결과와 실제 성과, 혹은 드러난 한계

---

저자들은 HouseFuzz 전체의 성능뿐만 아니라, 앞에서 설명한 세 가지 핵심 기법이 각각 실제 성능 향상에 기여하는지를 검증하기 위해 네 가지 연구 질문을 설정했다.

- **RQ1:** HouseFuzz 전체의 퍼징 성능은 기존 SoTA보다 우수한가?
- **RQ2:** 포괄적 서비스 식별은 더 많은 서비스를 찾아내는가?
- **RQ3:** 다중 프로세스 퍼징은 코드 탐색과 취약점 탐지에 기여하는가?
- **RQ4:** 서비스 프로토콜 기반 퍼징과 TDG는 유효한 입력 생성에 기여하는가?

> **논문 위치:** 8절 Evaluation

### 실험 환경과 데이터셋

실험은 다음 환경에서 수행되었다.

| 항목 | 구성 |
| --- | --- |
| 운영체제 | Ubuntu 22.04 |
| CPU | Intel Xeon Gold 5218, 2.30GHz, 64코어 |
| 메모리 | 245GB |

> **논문 위치:** 8.1절 Environment

기존 SoTA 연구에서 사용된 D-Link, Netgear, Trendnet의 펌웨어 이미지 70개를 기반으로 데이터셋을 구성했다. 그중 35개는 동일 제품의 최신 버전으로 교체했으며, 10개는 파일시스템 추출에 실패했다. 최종적으로 추출 가능한 펌웨어 이미지 60개를 사용했다.

| 제조사 | 전체 이미지 | 추출 성공 이미지 | 공통 테스트 서비스 |
| --- | --- | --- | --- |
| D-Link | 30 | 22 | 17 |
| Netgear | 29 | 29 | 20 |
| Trendnet | 11 | 9 | 4 |
| **합계** | **70** | **60** | **41** |

여기서 공통 테스트 서비스는 Greenhouse와 HouseFuzz가 모두 에뮬레이션하고 퍼징할 수 있는 웹 서비스다.

> **논문 위치:** 8.1절 Firmware Image Dataset, 표 2, 8.2.1절 Fuzzing Targets

각 서비스는 도구별로 24시간씩 3회 퍼징했다. 각 실행에는 CPU 코어 1개를 사용했으며, 동일한 파일시스템, 프로세스, 초기 시드를 사용했다. HouseFuzz의 퍼징 시간에는 오프라인·온라인 TDG 추론 시간도 포함되었다.

> **논문 위치:** 8.2.1절 Fuzzing Settings

비교 대상으로는 Firm-AFL, EQUAFL, Greenhouse를 검토했으며, 기존 평가에서 가장 높은 성능을 보인 Greenhouse를 최종 SoTA baseline으로 선택했다.

> **논문 위치:** 8.2.1절 Baseline Choice

### RQ1: 전체 퍼징 성능

41개 공통 서비스에서 HouseFuzz와 Greenhouse를 비교한 결과는 다음과 같다.

| 평가 항목 | Greenhouse | HouseFuzz |
| --- | --- | --- |
| 평균 edge code coverage | 11,072 | 14,767 |
| 탐지한 전체 취약점 | 46개 | 128개 |
| 탐지한 0-day | 40개 | 110개 |
| 취약점이 발견된 서비스 | 18개 | 25개 |

논문은 HouseFuzz의 edge coverage가 Greenhouse보다 **24.8% 높다**고 보고하며, 0-day 취약점을 **175% 더 많이 탐지**했다고 제시한다. 41개 서비스 중 36개에서는 코드 커버리지 차이가 통계적으로 유의했다. 다만 표 3의 수치인 11,072와 14,767을 Greenhouse 기준으로 계산하면 증가율은 약 **33.4%이므로**, 본문의 비율과 표 사이에 산술적 불일치가 존재한다.

> **논문 위치:** 8.2.1절 Results on Code Coverage, Results on Vulnerability Detection, 표 3

다만 두 도구를 공정하게 비교하기 위해 코드 커버리지에는 network-facing process의 edge coverage만 포함했다. 따라서 HouseFuzz가 데몬 및 유틸리티 프로세스에서 수집한 추가 커버리지는 이 수치에 포함되지 않는다.

또한 Greenhouse는 명령어 삽입을 탐지하지 못하므로, HouseFuzz가 발견한 명령어 삽입 취약점도 직접 비교에서 제외했다.

> **논문 위치:** 8.2.1절 Comparison Metrics

### RQ2: 서비스 식별 성능

HouseFuzz, FirmAE, Greenhouse가 60개의 펌웨어 이미지에서 식별한 network-facing process 수는 다음과 같다.

| 도구 | 식별한 프로세스 | 재현율 |
| --- | --- | --- |
| HouseFuzz | 311개 | 80.4% |
| FirmAE | 128개 | 33.1% |
| Greenhouse | 44개 | 18.1% |

수동 분석 결과 세 도구가 식별한 프로세스의 정밀도는 모두 100%였다. HouseFuzz는 기존 방식보다 최소 143% 더 많은 network-facing process를 식별했다.

> **논문 위치:** 8.3절 Results on Network-Facing Process Identification and Network Service Identification

HouseFuzz는 시스템 초기화 과정에서 85개의 에뮬레이션 예외를 탐지했으며, 그중 8개는 되돌리기 검증을 통해 오탐(false positive)으로 판별했다. 나머지 예외를 처리한 결과 23개의 펌웨어 이미지에서 네트워크 서비스를 119개, 즉 37% 더 많이 식별했다.

또한 Greenhouse와 FirmAE가 모두 식별하지 못한 웹 서비스 3개를 각각 72시간 동안 퍼징하여 **12개의 0-day 취약점**을 발견했다.

> **논문 위치:** 8.3절의 exception handling 분석과 Identified Vulnerabilities in Overlooked Services

이 결과는 서비스 식별 성능의 향상이 단순히 퍼징 대상 수만 증가시킨 것이 아니라, 기존 도구가 테스트하지 못했던 서비스에서 실제 취약점을 발견하는 데 연결되었음을 보여준다.

### RQ3: 다중 프로세스 퍼징의 효과

평가 대상 서비스의 53.7%에서는 network-facing process, daemon process, utility process 사이의 IPC가 관찰되었다. 모든 서비스가 세 유형 가운데 최소 두 종류의 프로세스를 포함했다.

> **논문 위치:** 8.4.1절 Ablation Experiment

다중 프로세스 프레임워크만 Greenhouse에 추가한 `HouseMP`는 Greenhouse보다 16개 서비스에서 더 높은 코드 커버리지를 달성하고, Greenhouse가 발견하지 못한 취약점 14개를 탐지했다.

그러나 전체 취약점 수는 Greenhouse의 46개보다 적은 39개였다. 다중 프로세스 피드백 수집에 필요한 실행 오버헤드로 인해 제한된 시간 안에 수행할 수 있는 테스트 케이스 수가 감소했기 때문이다.

> **논문 위치:** 8.4.1절, 표 6·7·8

HouseFuzz가 발견한 취약점을 수동 분석한 결과 다음 취약점이 실제 다중 프로세스 취약점으로 확인되었다.

- 기존 비교 데이터셋: 128개 중 3개
- 최신 펌웨어 데이터셋: 21개 중 15개

이러한 취약점에는 총 17개의 CVE/CNVD가 부여되었으며, 논문에서 보고한 전체 45개 CVE/CNVD의 38%를 차지했다.

> **논문 위치:** 8.4.2절 Multi-Process Vulnerability Analysis, 표 9

즉, 다중 프로세스 퍼징은 모든 서비스에서 전체 취약점 수를 일관되게 증가시키지는 않았지만, 단일 프로세스 퍼징으로는 도달하기 어려운 별도의 취약점 유형을 탐지하는 데 중요한 역할을 했다.

### RQ4: 서비스 프로토콜 기반 퍼징의 효과

저자들은 다음 네 가지 설정을 비교하여 표준 프로토콜과 TDG의 효과를 확인했다.

| 설정 | 다중 프로세스 | 표준 프로토콜 | 온라인 TDG | 오프라인 TDG | 취약점 |
| --- | --- | --- | --- | --- | --- |
| `HouseMP` | 사용 | 미사용 | 미사용 | 미사용 | 39개 |
| `HouseCFG` | 사용 | 사용 | 미사용 | 미사용 | 36개 |
| `HouseTDGOL` | 사용 | 사용 | 사용 | 미사용 | 69개 |
| `HouseFuzz` | 사용 | 사용 | 사용 | 사용 | 128개 |

> **논문 위치:** 8.5.1절, 표 7·8

표준 프로토콜 문법만 추가한 `HouseCFG`는 취약점 수를 증가시키지 못했다. 반면 커스텀 서비스 프로토콜의 토큰 의존관계를 온라인으로 추론한 `HouseTDGOL`은 69개의 취약점을 발견했고, 오프라인 TDG까지 결합한 최종 HouseFuzz는 128개를 발견했다.

이는 표준 문법만 따르는 것보다 펌웨어별 커스텀 의미 제약을 함께 모델링하는 것이 취약점 탐지에 더 중요하다는 것을 보여준다.

HouseFuzz가 생성한 TDG는 평균적으로 다음과 같은 크기를 가졌다.

- 토큰 노드: 734개
- 토큰 의존관계 간선: 2,610개

토큰 추론 정밀도는 62%로 Greenhouse 퍼징 사전의 15%보다 높았다. 토큰 의존관계 추론 정밀도는 44%였다.

> **논문 위치:** 8.5.2절 Study on TDG Inference Effectiveness

### 실제 취약점 탐지 성과

논문 전체 실험에서는 총 **177개의 취약점**을 발견했으며, 그중 **156개가 0-day 취약점**이었다.

0-day 취약점의 유형은 다음과 같다.

- 버퍼 오버플로: 58개
- OS 명령어 삽입: 15개
- 서비스 거부: 83개

저자들은 발견한 취약점을 책임 있게 공개했으며, 논문 작성 시점까지 **45개의 CVE/CNVD**를 부여받았다.

> **논문 위치:** 1절 Contributions, 8.1절 Vulnerability Disclosure, 표 9

기존 비교 데이터셋이 2019년 이전의 오래된 펌웨어 중심이라는 한계를 보완하기 위해, 2020년 이후 출시된 제품을 대상으로 별도의 취약점 탐색 실험도 수행했다.

45개 제품 중 파일시스템을 추출할 수 있었던 12개 펌웨어의 웹 서비스를 각각 24시간 퍼징하여, 5개 서비스에서 **21개의 0-day 취약점**을 탐지했다. 이 21개 취약점에는 모두 CVE/CNVD가 부여되었다.

> **논문 위치:** 8.2.2절 Vulnerability Hunting Experiment, 표 4

### 결과를 통해 확인된 한계와 트레이드오프

#### 1. 다중 프로세스 계측의 효과와 비용

HouseFuzz의 다중 프로세스 피드백 수집과 TDG 추론은 Greenhouse보다 평균 **6.8배 높은 시간 오버헤드**를 발생시키며, 활성 프로세스마다 128KB 크기의 커버리지 비트맵이 추가로 필요하다. `HouseMP`는 새로운 실행 경로와 Greenhouse가 놓친 취약점 14개를 발견했지만, 계측 오버헤드로 실행량이 감소하여 전체 취약점 수는 46개에서 39개로 줄었다. 이는 탐색 범위와 처리량 사이의 명확한 트레이드오프를 보여준다.

> **논문 위치:** 8.2.1절 Results on Vulnerability Detection, Results on Overhead, 8.4.1절 Ablation Experiment

#### 2. TCE 탐지 범위의 제한

현재 TCE 탐지는 IPC 요청을 기다릴 때 `select()`와 `poll()`을 사용하는 서비스를 가정한다. `inotify` 등 다른 시스템 호출을 사용하는 서비스는 추가 구현이 필요하다.

또한 여러 IPC 이벤트를 동시에 처리하는 `select()`의 비결정적 동작으로 인해 일부 테스트 케이스에서는 실행마다 코드 커버리지가 달라졌다.

> **논문 위치:** 8.4.3절 Experiment on TCE Detection Stability, 10절 Limitations of TCE Detection

#### 3. TDG 추론의 부정확성

오프라인 TDG 추론은 정적 분석의 불완전성과 비건전성 때문에 오탐(false positive)과 미탐(false negative)을 생성할 수 있다.

온라인 분석은 문자열 비교의 실제 데이터 의존관계를 직접 분석하지 않고 미리 정의된 토큰 유형에 의존한다. 계측되지 않은 커스텀 비교 API에서 사용되는 토큰도 놓칠 수 있다.

토큰 의존관계 추론 정밀도는 44%였으며, ground truth가 없기 때문에 TDG의 재현율은 측정하지 못했다.

> **논문 위치:** 8.5.2절, 10절 Limitations of TDG Inference

#### 4. 프로세스 에뮬레이션에 대한 의존

HouseFuzz는 프로세스 에뮬레이션에 Greenhouse를 사용하므로 Greenhouse의 한계를 상속한다. Greenhouse는 추출된 펌웨어 이미지 가운데 19개를 테스트하지 못했고, HouseFuzz의 초기화 예외 처리도 모든 에뮬레이션 문제를 해결하지는 못했다.

> **논문 위치:** 10절 Limitations of Process Emulation

#### 5. 펌웨어 추출 단계의 한계

기존 데이터셋에서는 70개 중 10개, 최신 펌웨어 데이터셋에서는 45개 중 33개의 파일시스템을 추출하지 못했다. 저자들은 최신 펌웨어가 새로운 패킹 방식을 사용하기 때문일 가능성을 제시한다.

이는 HouseFuzz의 퍼징 기술과 별개로, 펌웨어 파일시스템을 추출하지 못하면 분석 파이프라인 자체를 시작할 수 없다는 현실적인 한계를 보여준다.

> **논문 위치:** 8.1절 Firmware Image Dataset, 8.2.2절 Fuzzing Targets

#### 6. 인증 이후 코드에 도달하기 어려움

서비스가 인증을 요구하면 HouseFuzz는 권한이 필요한 코드까지 도달하지 못할 수 있다. 따라서 인증 이후에 존재하는 취약점을 놓치거나 코드 커버리지가 제한될 수 있다.

> **논문 위치:** 10절 Authentication Handling

> 💡 **질문 : 퍼징 과정에서 우연히 인증 검사를 통과하여 인증 이후 코드에 도달할 가능성은 없는가?**
>
> ---
>
> 이론적으로 가능하지만 현실적으로는 어렵다. 인증에는 정확한 자격 증명뿐 아니라 로그인 순서, 세션 쿠키, 토큰 등 상태 유지가 필요하며, 인증 실패 입력에서는 정답에 가까워졌다는 커버리지 피드백도 얻기 어렵다. 따라서 무작위 변형으로 인증을 통과하기보다는 정상 로그인 후 인증 세션을 유지한 상태에서 퍼징해야 한다.

#### 7. 알려지지 않은 프로토콜 처리의 한계

평가 대상 서비스의 32.4%는 잘 알려지지 않은 프로토콜을 사용했다. 이러한 서비스는 표준 프로토콜 문법을 구하기 어려워 프로토콜 기반 입력 생성의 효과가 제한된다.

저자들은 향후 protocol reverse engineering이나 structure-aware fuzzing을 결합하는 방안을 제안한다.

> **논문 위치:** 10절 Unknown Service Protocols, 표 5

### 종합

HouseFuzz는 포괄적 서비스 식별, 다중 프로세스 퍼징, TDG 기반 입력 생성을 결합하여 기존 방식이 놓쳤던 서비스·프로세스·입력 공간을 확장한다. 다만 높은 실행 오버헤드와 불완전한 프로토콜 추론, 프로세스 에뮬레이션 의존성을 동반하므로, 핵심 성과는 속도 자체보다 **탐색 범위를 넓혔다는 점**에 있다.

## 내가 느낀 점, 배운 점, 이후 해볼 만한 확장 아이디어

---

이 논문을 통해 펌웨어 퍼징의 성능은 단순히 입력 변형 알고리즘을 개선하는 것만으로 높아지는 것이 아니라, **무엇을 하나의 서비스로 볼 것인지**, **어느 프로세스의 실행 피드백을 수집할 것인지**, **어떤 입력이 서비스에 의미가 있는지**를 정확하게 모델링하는 것에 따라 달라질 수 있다는 것을 알게 되었다.

이 논문을 읽으며 가장 인상 깊었던 부분은, 펌웨어 퍼징의 대상을 하나의 바이너리가 아니라 서로 협력하는 **서비스 단위**로 확장한 것이다. 외부 요청을 받는 프로세스에서 취약점이 발생하지 않더라도, IPC로 연결된 데몬 프로세스에서 실제 취약점이 발생할 수 있다는 것을 깨달았기 때문이다.

또한 서비스 프로토콜 기반 퍼징 실험의 효과를 보며, 더 깊은 코드 경로에 도달하기 위해 커스텀 서비스 프로토콜의 의미적 제약을 고려한 입력 변형이 중요하다는 것을 느끼게 되었다.

이러한 관점은 현재 진행 중인 IP 카메라 취약점 분석에도 적용할 수 있을 것이라고 생각한다. 웹 서버나 영상 스트리밍 프로세스를 개별적으로 분석하는 데 그치지 않고, 펌웨어의 초기화 과정과 IPC를 추적하여 CGI 프로그램, 설정 관리 데몬, 인증 모듈 등 서비스에 관여하는 프로세스를 함께 식별할 필요가 있다. 이를 통해 외부 요청이 내부 프로세스까지 전달되는 경로와, 실제로 취약한 코드가 실행되는 위치를 더 정확하게 파악할 수 있을 것이다.

또한 IP 카메라에서 사용하는 HTTP·RTSP·ONVIF와 제조사별 커스텀 프로토콜의 입력 구조를 분석하여, 파라미터 간 의존관계와 세션 상태 같은 의미적 제약을 입력 생성에 반영해 볼 수 있다. 특히 인증이 필요한 기능은 퍼징으로 인증 절차를 우연히 통과하기를 기대하기보다, 정상 로그인으로 유효한 세션을 확보한 뒤 인증 상태를 유지하면서 요청을 변형하는 방식이 더 효과적일 것이다.

이후에는 IP 카메라의 외부 요청이 어떤 IPC를 거쳐 내부 데몬으로 전달되는지 서비스 단위로 구조화하고, 관련 프로세스의 코드 커버리지와 충돌 정보를 함께 수집하는 다중 프로세스 퍼징을 시도해 보고 싶다. 다만 모든 프로세스를 동시에 계측하면 실행 오버헤드가 커질 수 있으므로, 우선 공격 가능성이 높은 서비스와 요청 경로를 선별하여 적용하는 것이 현실적일 것으로 생각한다.

### 앞으로 할 것

- **추가로 읽을 논문:** Greenhouse, USENIX Security 2023
- **나의 프로젝트에 활용:** HouseFuzz 공개 구현을 실행하여 논문의 실험 환경을 재현하고, 현재 분석 중인 IP 카메라 펌웨어의 웹·RTSP·ONVIF 서비스에 적용할 수 있는지 확인한다. 우선 서비스 관련 프로세스와 IPC 경로를 식별한 뒤, 다중 프로세스 코드 커버리지 수집과 프로토콜 기반 입력 변형을 단계적으로 적용한다.

HouseFuzz는 시스템 초기화를 계속 진행하기 위해 예외 코드를 패치하고, 문제가 발생하면 일부 변경을 되돌린다. 그러나 서비스가 정상적으로 실행된다는 사실만으로 패치 이후의 실행 흐름과 프로세스 간 상호작용이 실제 펌웨어와 동일하다고 볼 수 있는가? 패치 때문에 실제 취약 경로가 제거되거나 원래 존재하지 않던 경로가 만들어질 가능성은 없는가?

> **관련 위치:** 5.1절, 8.3절, 10절 Limitations of Process Emulation
